## 二、设计/正确性问题（不明显报错，但会咬人）

### 6. 「墙钟上限」封不住进程，只封住了排序

`run.py:44-64` 用 `wait(timeout=60)` + `shutdown(wait=False, cancel_futures=True)`，注释与提交信息
（`4f2f492 fix: 抓取加墙钟上限，单个源挂起不再拖死整轮`）声称不会再被单源拖死。

实测（Python 3.13）：`main()` 0.2 s 返回，**进程 3.3 s 才退出**——
`ThreadPoolExecutor` 的线程是非守护的，解释器退出时 `_python_exit` 会 join 它们。
`future.cancel()` 对已在跑的线程返回 False，日志说「跳过」但线程还在下载。

后果：评分确实不再被拖死，但 **CI job 的墙钟仍由最慢的 socket 决定**，`urlopen(timeout=20)` 是单次
socket 操作超时、不是总时长上限。云端真遇到挂起时，60 s 上限名不副实。

### 7. 同一天的 `content/issues/<date>.json` 有**两个生产者**（最严重的架构问题）

- 云端 12:00：用自己的池（约 50 条）选 top 15，写 issue。
- 本机 12:15：`--dry-run` **重新抓一遍**拿到自己的池，再 `--refresh` 重建 issue 并推送。

`5c5f8c6 content: 2026-11-01 中文摘要` 的 diff 证明它不只提交了 summaries，**同时把
`issues/2026-11-01-12.json` 整份改了（210 行）**。也就是说云端 12:00 那版 15 条被本机结果覆盖。

实测后果（同一天两次抓取）：候选池 50 条 → 48 条（HN 那次失败）；当期 15 条里有 **2 条的 id 在新的池里
已经不存在**，另有 6 条在新池里排 20 名之后。日内容因此**不可复现**，且「AI 在池内重排」在这条链路上
实际变成了「本机重选一遍」。

`docs/ranking.md §6` 承诺「AI 只能重排、不能捞池外」——现在池的边界每天由本机决定，这条承诺没有实现基础。

**建议**：云端把候选池一并发布（例如 `content/pools/<date>.json` 或站点 `data/pools/`），
本机只读云端那一份；或者干脆规定「只有云端能写 issues，本机只写 summaries」，并用断言卡死。

### 8. 摘要 id 对不上时静默丢弃

`build.apply_summaries` 里 `extra = summaries.get(item["id"])`，取不到就 `continue`，没有 warn、没有计数。
AI 写错 id / 池变了 → 那一条悄悄退回英文标题，日报上看不出「本该有摘要但没有」。

### 9. `--dry-run` 有副作用，且会覆盖 12:15 要用的池

`run.py` 先把池写到 `05_Datas/interim/pool_<date>.json`（L175-176），再判断 `args.dry_run`（L188）。
help 写的是「只抓取并打印候选池，不生成页面」——实际**会落盘覆盖**。
审阅时我跑了一次 `--dry-run`，池就从 50 条被换成 48 条；若此刻有人跑 `--refresh`，
当期内容会跟着变。这是「只读命令改状态」，很危险。

### 10. `dropped` 字段是垃圾数据

`--refresh` 路径 `dropped = len(pool)`（L163），于是**公开的期次 JSON 里写着 `"dropped": 50`
/`48`**，语义是「淘汰了等于全部候选的数」。实测确认：删空摘要后 `--refresh` 出来 `dropped=48`。
已上线，任何人都能读到。

### 11. 产物目录只增不减

`build.render_site()` 只 `mkdir` + 拷贝，从不清理 `SITE_OUT`。实测本地残留：

```
03_OutputFiles/deliverables/site/data/issues/2026-11-01-12.json   ← v1 档位期次
03_OutputFiles/deliverables/site/data/issues/2026-11-01-18.json   ← 已删除的 18:00 档
```

线上暂时干净，只是因为 CI 每次全新克隆、产物目录从零生成；**本地发布一次就会把死数据推上去**。
同一目录下还留着一个 `.git`（本地跑过发布步骤），是嵌套仓库，总规则明确要避免。

### 12. 期次按钮数 > 内嵌期次数

`app.js MAX_CHIPS = 16`，`build.EMBED_RECENT = 14`。第 15、16 个按钮必然走 `fetch`。
而需求 C4 明确要求「本地双击打开副本」——`file://` 下 `fetch` 被 CORS 拦，这两个按钮点了就是
「这一期不在离线包里」。离线场景下 2/16 的功能是断的。

## 三、工程质量与卫生

13. **摘要素材本身质量不齐**：按来源统计候选池 excerpt 长度——InfoQ 11 条**全是「点击查看原文>」（7 字）**，
    量子位平均 22 字，TechCrunch 125 字。48 条里 17 条 < 20 字。
    而 `score` 对 `len(summary) < 20` 一律 `-1` → **系统性压低 InfoQ/量子位**，
    结果 48 条候选里 17 条来自 TechCrunch。这是「摘要长度」而不是「重要性」在决定排序。
14. **`content:encoded` 完全没解析**：`_localname("{...content/}encoded")` 得到 `encoded`，不在字段表里；
    而 `fields.setdefault(name, "" if name == "content" else ...)` 又让 `content` 永为空串。
    注释说「content 常含完整正文，只在没有 summary 时才用」——**这个兜底永不生效**，是假代码。
    （本次 TechCrunch feed 确实不带 `content:encoded`，所以没暴露；换个源就会缺摘要。）
15. **零测试、零依赖声明**。只用标准库值得表扬，但「接手测试」第 3 条要求「敢改、知道改坏了怎么退」——
    现在唯一的回路是「跑一次看页面」。`rank.py` 的分数/去重、`app.js` 的已读与期次切换都没有回归网。
16. **手写产物落在 gitignore 目录**：`03_OutputFiles/reports/digest_2026-11-01.md` 不在 git 里，
    且标题是「**午间版**」（v1 口径）。它不是任何脚本生成的，属于「手写文档」放进了可重建产物区。
17. **空目录无 `.gitkeep`**：`00_InputFiles/`、`02_Config/`、`05_Datas/*` 都不进 git，
    克隆下来六区只有四个，违反总规则 §1「空目录用 .gitkeep 占位」。
18. **验收清单 8 项全 `[ ]` 未勾，README 全打 ✅**
    （`requirements §5` 第 58-67 行 vs `README` 第 48-57 行）。
    且「Actions 定时 ✅ 已生效」依据的是 `workflow_dispatch` 试跑——
    上线至今**没有一条 `schedule` 触发的运行记录**（首次排期在 11-02 04:00 UTC）。属「未跑就声称」的灰区。
19. **总工作区 `AGENTS.md §7 工程清单` 未登记本工程**（`2026-10-python-engineering` 也漏了）。
20. 零碎：`build.CATEGORY_ORDER` 死常量；`data/index.json` 生成了但前端从不读；
    `build.build_issue` 与 `build.apply_summaries` 各写一遍「合并摘要 + 重排」，语义重复且行为不完全一致；
    前端 `esc()` 不拦 `javascript:` 协议；`fetch_bytes` 无体积上限（超大 feed / gzip 炸弹）。

## 四、确实做对的

- **降级是真的可降级**：副本里删空 `summaries/` 后 `--refresh`，仍产出 15 条、页面完整可读、
  `has_ai_summary=false`，标题回落 `title_orig`。ADR 0001 不是纸面承诺。

- **`paths.py` 严格**：向上找根，找不到抛异常，没写「固定深度兜底」。

- **幂等**：`--rerender` 连跑两次 `git status` 干净，`apply_summaries` 有「变了才写」判断。
- **CI 全绿**，gh-pages 发布链路通，线上 `data.js` 有 15 条真实内容。

1. `site/index.html` 两行文案 + `app.js`「这一档」——1 分钟，用户可见。

6. 补 `.gitkeep`、勾验收清单、把「Actions 定时」改成「待 11-02 首次 cron 验证」。
7. 有余力再补：`rules` 的单测（`score`/`dedupe` 纯函数好测）、`content:encoded` 解析、
